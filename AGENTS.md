# Japan Legal Reform Watch by LegalOS — Notes for Codex

This file has a twin: `AGENTS.md` is read by Codex and `CLAUDE.md` by Claude Code. Apart from the title line they must stay identical, so change both in the same commit; `tests/test_agent_instructions_in_sync.py` fails when they differ.

## Project mission

A free, browser-based dashboard that surfaces Japanese legal, regulatory, public comment, and administrative developments in **English** for foreign companies, in-house counsel, and compliance teams.

The audience cannot read Japanese fluently and is using this tool to triage which Japanese-language source documents deserve closer attention. Treat that audience expectation as load-bearing: this is a triage layer, not a substitute for primary sources or qualified counsel.

## Current scope (this iteration)

- Static browser dashboard, no backend, no build step.
- The **canonical published file `docs/data/legal_updates.json` is generated** by `scripts/build_public_data.py` from `data/raw_items.json` (provisional, rule-based). It is uncapped. `scripts/build_public_archives.py` deterministically derives an uncapped shard per publication year plus `undated`, with a manifest used by the browser. `data/legal_updates.json` remains only as the original hand-curated sample / schema reference and is no longer kept in sync with the published file.
- Published for **GitHub Pages serving from `/docs`** — the site under `docs/` is self-contained.
- **Four pipeline scripts exist:** `scripts/fetch_updates.py` (→ `data/raw_items.json`, raw fetch), `scripts/build_public_data.py` (→ `docs/data/legal_updates.json`, provisional rule-based mapping), `scripts/summarize_updates.py` (optional Stage 3 Claude English and Japanese summarization), and `scripts/translate_updates.py` (optional Stage 4 Claude Simplified-Chinese translation for the published items). Stages 3–4 are active in the daily workflow when `ANTHROPIC_API_KEY` is available; the published corpus and caches contain real API-generated summaries and translations, while unsummarized or untranslated fields retain their documented fallbacks.
- **GitHub Actions daily update workflow exists** at `.github/workflows/daily-update.yml` for manual runs and a daily 21:00 UTC schedule (06:00 JST). It commits only the pipeline data/cache/health files, the uncapped canonical public JSON, its archive manifest, and yearly shards when tracked data changes, then explicitly requests a GitHub Pages build from the latest default-branch revision. The workflow first runs `py_compile` on the pipeline scripts and the offline regression tests (`python -m unittest discover -s tests`); any failure stops the job **before** the network fetch, build, summarize, translate, archive, and commit steps. `ANTHROPIC_API_KEY` is exposed only to the summarize and translate steps, never to the tests. Archive generation runs after translation and before the change check.
- **Source Health Monitor exists for administrator-facing GitHub Actions monitoring only.** It evaluates per-source raw fetch counts from `logs/source_fetch_report.json`, updates minimal streak state in `data/source_health_state.json`, writes a GitHub Step Summary, and enforces the final gate only after the commit step. It must not be shown in the public dashboard UI.

## Conventions

- The dashboard UI defaults to **English (canonical)** and offers optional **Japanese (`ja`)** and **Simplified-Chinese (`zh-Hans`)** displays via a header language selector. English remains canonical for the international triage layer. Japanese mode uses the original `title_ja` and optional Stage 3 `*_ja` summaries generated directly from Japanese source metadata; it is not an English-to-Japanese translation. Chinese remains an unofficial Stage 4 translation and falls back to English per field.
- **All user-facing strings route through the i18n layer (`docs/i18n.js`, `window.JLRW_I18N`).** English values there mirror the existing UI exactly; `applyStatic()` overlays the active language onto `[data-i18n]` / `[data-i18n-placeholder|aria-label|title]` elements and restores English loss-lessly. Do not scatter `if (lang === "zh-Hans")` branches across `app.js`; add a key/label to `i18n.js` instead. `i18n.js` must be loaded **before** `app.js`.
- The language selector follows precedence **URL (`lang=ja` or `lang=zh-Hans`) > `localStorage` (`jlrw-language`) > English**; `lang=en` is omitted from the URL, unknown values fall back to English, and `document.documentElement.lang` is updated. Switching language preserves all filters/sort/quick-filter state and the Load more window (it does not reset to 50).
- Preserve a **measured, corporate-legal tone** in all textual content. Avoid marketing hype, alarmist phrasing, or punchy verbs.
- All copy must be framed as **summary, not advice**. Never imply a legal conclusion for a specific party.
- Never claim our summaries are official, certified, or comprehensive.
- Source attribution is **mandatory** for every item (`source_name` + `source_url`).
- The dashboard-level trust notice must clarify that AI summaries and rule-based previews are monitoring aids, not legal advice, and that original Japanese official sources remain authoritative.
- The dashboard displays a compact Data status summary computed client-side from the selected period JSON: selected period, selected updates, all-years archive total, sources represented, localized content coverage, open public comment count, Newly detected count for the last 7 days, and latest checked date. Localized coverage means English AI summaries in English, Japanese-source AI summaries in Japanese, and complete Simplified-Chinese translations in Chinese; these labels and counts must not conflate translation with summarization. It must not claim complete coverage or successful checking of every source.
- Card source buttons must link to each record's original Japanese official source using `source_url`. English summaries and previews are triage aids only; the original Japanese official source remains authoritative.
- Each update card includes client-side copy actions. `Copy summary` copies a plain-text English monitoring summary with the official source URL; `Copy source link` copies the original Japanese official source URL. These actions do not change data, and original Japanese official sources remain authoritative.
- The dashboard supports client-side CSV export for the current filtered dataset. Export includes all matching updates, not only currently rendered cards, respects current filters and sort order, includes official Japanese source URLs, and includes a `First detected` column. It is a convenience feature; original Japanese official sources remain authoritative. **English export is unchanged (16 columns).** Japanese uses a fixed 16-column layout with the Japanese original title plus an English reference title; Chinese uses the existing fixed 17-column translated-title layout. Both localize labels/source names, fall back safely, and keep internal ID last. All column orders are pinned by tests.
- Dashboard filters include `Area`, `Stage`, `Source`, and `Impact Level`; the Source filter is populated from `source_name`. Quick filters provide one-click views for `Public Comment Open`, `AI Summary`, `Newly detected`, and `Medium Impact`, plus a full Reset.
- The dashboard supports Sort by `Relevance`, `Published date`, `Last checked`, and `First detected`. Published date is the default so the newest official updates appear first; Relevance preserves the composite ranking generated by `build_public_data.py`, including stage, impact, and recency adjustments. Sort applies to the full filtered dataset before the 50-card render window. Filter/sort/period state is reflected in URL query parameters (`q`, `area`, `stage`, `source`, `impact`, `sort`, `ai`, `new`, `year`, `lang`), where `sort` supports `relevance`, `published`, `checked`, and `detected`, `new=7` is the only valid Newly detected URL parameter, `year` supports a manifest year, `undated`, or `all`, and non-default `lang` supports `ja` or `zh-Hans`. The latest year and English omit their params; Load more state is not persisted. Reset returns to the latest year and Published date while clearing other URL state, but does not change language.
- On mobile, filters/search collapse behind a compact `Filters & Search` toggle, with active filters summarized so shared URLs remain understandable. Desktop keeps the full filter layout; the mobile open/closed state is not persisted in the URL, while URL filter state, Sort, Load more, and copy actions remain supported.
- **Source names display English-first** via the `SOURCE_DISPLAY_NAMES` map in `docs/app.js` (e.g. `Japan Fair Trade Commission (JFTC)`); the underlying `source_name` values in the published JSON and the filter option VALUES stay unchanged. When adding a source to `fetch_updates.py`, add both its English display name and compact URL slug to `docs/app.js` (tests enforce this).
- The dashboard loads the latest yearly shard by default and initially renders **50 cards**, adding 50 per **Load more** click. The Period selector can load any manifest year, `Undated`, or `All years (slower)`; every year is uncapped and All years loads the uncapped canonical file. Search, filters, quick filters, filter options, the results meta line, and CSV export operate on the full selected period, not merely rendered cards. Any filter or period change and Reset returns the visible window to 50. Free-text search always matches the English title, original Japanese title (`title_ja`), and Simplified-Chinese translated title regardless of active UI language. For `summary_source: "claude"` records it additionally matches the English summary and Simplified-Chinese summary / business-impact / recommended-action fields. Complete Japanese `*_ja` summaries are independently searchable regardless of the English `summary_source`. Rule-based or missing-source placeholder bodies are deliberately excluded from search so shared boilerplate cannot create false-positive monitoring matches.
- `Newly detected` means the item was first appended to this dashboard's continuing raw history, shown for valid `first_seen_at` dates in the last 7 calendar days. It does **not** mean a new law, new regulation, enactment date, amendment date, or first government publication date. Existing legacy items without `first_seen_at` are not backfilled and are not shown as Newly detected.
- The dashboard footer includes modest links to Legal GPT, the Japan Legal Reform Watch landing page, and Japan legal updates, while keeping the EN/JA disclaimer links visible.
- **The site is served at `https://updates.legal-gpt.com/`** (custom domain since 2026-10-07; `docs/CNAME`). GitHub Pages 301-redirects the old `legal-gpt-official.github.io/japan-legal-reform-watch/` URL, so links already sent keep working. `alert_common.SITE_URL` is the single source for absolute URLs (feeds, digest, Stripe return URLs) and a test ties it to `docs/CNAME`. The `.ics` event UIDs deliberately keep the old `@legal-gpt-official.github.io` host: a UID is an identifier, and changing it would duplicate every event in subscribed calendars.
- **Search visibility.** The cards render client-side, so `scripts/build_public_pages.py` (daily, after the feeds) writes the 20 newest official publications as a static list between the `STATIC-LATEST` markers inside `#cards` in `docs/index.html` — `app.js` replaces it with the interactive cards on load, so crawlers and visitors see the same records — and writes `docs/sitemap.xml`. The block shows an item's summary only when it is an AI summary (the rule-based template is identical on every item), escapes every field, links only http(s) source URLs, and carries the monitoring-aid notice. It also writes a `Browse … by area` link list between the `AREA-NAV` markers, one static landing page per area channel at `docs/areas/<slug>/` (`AREA_PAGES`: a search-oriented heading such as "Japan Energy & Environmental Regulation Updates", a factual topic line, open public comments soonest-deadline first, the 30 newest updates, the most frequent sources, and links to the filtered dashboard, the area RSS feed, and calendar), and a cross-area `docs/public-comments/` page of open consultations with a trusted structured deadline. Slugs are public URLs — never rename a published one; a test requires exactly one page per non-`all` channel. These pages are English-only, load only `style.css` and `analytics.js` (no app JS), say that area labels come from keyword rules, and carry a visible reliability notice plus the disclaimer links in place of the dashboard's modal. `Other` gets no page: it has no search intent. `STYLE_CACHE_BUSTER` in the script must equal the `style.css?v=` in `index.html` (tested). Output is deterministic; do not hand-edit between the markers. `index.html` sets a canonical URL to the site root so URL-state variants (`?area=…`) are not indexed separately. `robots.txt` must never disallow `docs/data/`, or rendered pages come out empty. A visible `Follow for free` strip links the all-areas RSS feed and deadline calendar and opens the area-feed section of the alerts dialog.
- Do not introduce external runtime dependencies (CDN fonts, analytics, trackers, JS frameworks) without explicit approval. The current dashboard is deliberately dependency-free apart from one approved exception (2026-10-06): the cookieless **Cloudflare Web Analytics** beacon, loaded only through `docs/analytics.js` from `static.cloudflareinsights.com`, with `spa: false` so filter/URL-state changes are not counted as page views. It loads nothing while its public site token is empty; when the token changes, bump the `analytics.js?v=` cache buster in `docs/index.html` and `docs/alerts/thank-you.html`. No other analytics host, cookie, or tracker is approved, and traffic figures are never shown in the public UI.
- **Access report email (owner-only).** `scripts/send_access_report.py`, run by `.github/workflows/access-report.yml` at 23:50 UTC (08:50 JST, so GitHub's schedule delay lands it around 09:00), queries the Cloudflare GraphQL Analytics API (`rumPageloadEventsAdaptiveGroups`, `count` = page views, `sum.visits` = visits) and sends one Japanese email through Resend to `ACCESS_REPORT_TO`: the previous JST day every day, the previous Monday-Sunday week on Mondays, and the previous calendar month on the 1st, each against the period before it. Periods are JST days converted to UTC instants; queries are split into 7-day chunks and summed. Visits are not unique visitors and the figures are sample-based estimates; the email says so. The workflow is read-only (`contents: read`), and because its log is public the script prints no figures, recipient address, account id, site tag, or token. The scheduled run uses a per-JST-day Resend `Idempotency-Key`; a manual run adds its run id so it can resend. Settings: secrets `CLOUDFLARE_API_TOKEN` (Account Analytics: Read), `CLOUDFLARE_ACCOUNT_ID`, `ACCESS_REPORT_TO`, existing `RESEND_API_KEY`; variables `CLOUDFLARE_WEB_ANALYTICS_SITE_TAG` and existing `ALERT_FROM_EMAIL`. Until they are set the run warns and exits 0; a Cloudflare or Resend failure fails the run. The manual `list-sites` mode prints site tags for setup, and the manual-only `periods=today` section (today so far against all of yesterday; never scheduled and not part of `all`) lets the figures be checked against the Cloudflare dashboard on the day of setup.
- **Email alerts are self-serve; nothing may require an operator.** The paid daily digest (US$19/month or US$190/year) is sold through Stripe Payment Links whose required `area` dropdown is built from `scripts/alert_common.CHANNELS`, with one pair of links (monthly/yearly) per dashboard language because Stripe never translates custom-field labels: `checkoutLinks` (English) and `localizedCheckoutLinks` (`ja`, `zh-Hans`) differ only in labels and the checkout note, store identical channel values, and are opened with Stripe's `locale` URL parameter (`en`/`ja`/`zh`) to match; a language without a link falls back to the English link unchanged. Keep `alert_common.AREA_LABELS`/`ALL_AREAS_LABELS` equal to the dashboard's area names in `docs/i18n.js` (a test enforces it), and state that the digest email itself is in English; customers cancel, switch billing, change the delivery email, and download invoices in the Stripe customer portal. Do not reintroduce inquiry forms, manual activation, manual reconciliation, or review-required drafts. The dashboard collects no contact or payment data; `docs/alerts-config.js` holds only the public Payment Links (`buy.stripe.com`) and portal login URL (`billing.stripe.com/p/login/`), and `app.js` accepts no other host.
- A live channel `value` in `alert_common.CHANNELS` is stored by Stripe on every subscription: add channels freely, never rename or remove a live value. Channel areas must equal the classifier's areas minus `Other` (a test enforces it). The free tier is the static per-channel RSS feed and `.ics` deadline calendar written to `docs/feeds/` by `scripts/build_public_feeds.py`.
- `scripts/send_alert_digests.py` runs on scheduled runs only, before the data commit, with `continue-on-error`. It reads subscribers from Stripe at run time and must never write an email address to the repository, `data/alert_digest_state.json`, previews, or logs (the Actions log is public). It sends one recipient per Resend request with a per-subscription, per-JST-day `Idempotency-Key`; content is limited to already-published fields plus the Newly detected caveat, disclaimer, and portal link. The state file (published item ids only) is written only after Stripe was read and not every send failed, so outages defer items rather than drop them. `scripts/setup_alert_billing.py` is the one-time, idempotent Stripe setup; it defaults to a read-only plan and never prints the key.
- Treat `docs/alerts-config.js` as a cache-sensitive public integration file. When it changes, bump the shared `?v=` cache buster in `docs/index.html` and `docs/alerts/thank-you.html` in the same commit so visitors do not retain obsolete payment links.
- While a checkout link is available, the paid section states that completing checkout means agreeing to the digest's Terms of Service and links to those terms (`https://legal-gpt.com/japan-legal-reform-watch-terms/`), the Specified Commercial Transactions Act disclosure (`https://legal-gpt.com/commerce-disclosur/`), and the privacy policy (`https://legal-gpt.com/privacy-policy/`); `docs/alerts/thank-you.html` repeats the three links. The terms page is Japanese (authoritative) followed by an English reference translation, so `I18N.subscriptionTermsUrl()` opens the page for `ja` and its `#jlrw-terms-en` section otherwise. Those pages are maintained in WordPress on legal-gpt.com, outside this repository: when the price, renewal, cancellation, refund rules, or digest contents change, update them in the same release. Every Payment Link also requires Stripe's Terms of Service checkbox (`consent_collection.terms_of_service=required`) beside per-language text that links the same targets (`setup_alert_billing.TERMS_URLS`). Stripe accepts the checkbox only while the account's public details carry a terms of service URL. `setup_alert_billing.py` updates an existing link's consent setting and checkout text in place, so the published Payment Link URLs do not change.
- **Treat all record/source data as untrusted.** Every value rendered into the DOM must pass through `escapeHtml()`; `source_url` must also pass `safeUrl()` (scheme allow-list) **and** `escapeHtml()` before being placed in an `href`. This boundary prevents markup/script injection once automated ingestion is added.

## Data schema (`data/legal_updates.json`)

Each entry contains:

- `id` — stable string id (e.g., `jlrw-2026-001`).
- `title_en` — unofficial English title label; rule-based at Stage 2, AI-generated only after Stage 3.
- `title_ja` — original Japanese title.
- `area` — rule-based subject area, e.g. `Data / Privacy / AI`, `Finance / AML`, `Healthcare / Pharmaceuticals`, `Food / Agriculture`, `Transport / Infrastructure`.
- `stage` — e.g., `Public Comment Open`, `Public Comment Closed`, `Public Comment Results Published`, `Bill Submitted`, `In Force`, `Enforcement Action`, `Court Decision`.
- `impact_level` — `High` | `Medium` | `Low`.
- `summary_en`, `business_impact_en`, `recommended_action_en` — short paragraphs.
- `source_name`, `source_url` — original Japanese authority and link.
- `published_at`, `last_checked` — ISO `YYYY-MM-DD`.
- `first_seen_at` — optional ISO `YYYY-MM-DD` for items first detected by this dashboard after the feature is deployed; absent for legacy / unknown items.
- `comment_deadline` — optional structured public-comment deadline as an ISO date or offset date-time. It is used only to close an otherwise `Public Comment Open` item after a trusted deadline; absent when no trusted value exists.
- `comment_deadline_source` — optional deadline provenance: `source_metadata` for the item's own structured metadata or `related_egov_item` for a conservatively matched e-Gov item.
- `comment_deadline_source_id` — present only for an inherited deadline; the related e-Gov item's stable ID.
- `comment_deadline_inherited` — optional boolean provenance flag; `true` only for a deadline inherited from a related e-Gov item.
- `summary_ja`, `business_impact_ja`, `recommended_action_ja` — optional all-or-none Stage 3 Japanese AI summaries generated directly from `title_ja` / Japanese `raw_summary`; they are not translations and are independent of whether the English body is AI-generated or rule-based. `summary_ja_source: "claude"`, `ja_summarized_at`, and `ja_summary_model` provide their independent provenance. The UI falls back to English only while they are absent.
- `translations` — optional Stage 4 translations object. Currently only `translations.zh-Hans = { title, summary, business_impact, recommended_action }` (Simplified Chinese) is supported. It is an **unofficial AI aid**; English fields stay canonical. Items with no translation omit the block entirely (no empty `translations`); the UI and CSV fall back to English per field.

## Ingestion (`scripts/fetch_updates.py`)

- Stage 1 **raw fetch only**: pulls a curated 24-source `SOURCES` list of official Japanese feeds, APIs, and update pages into `data/raw_items.json`. It includes **JPX public comments**, **Tokyo Stock Exchange rule revisions**, **PMDA safety updates**, **JSDA public comments and results**, the Courts site's **recent Supreme Court decisions**, focused **SESC enforcement updates**, and **NTA current updates and circulars**, in addition to the ministry, regulator, Diet, and e-Gov sources. NTA parses only the two current Shift_JIS `index_news` tables, excludes collapsed archive tables, and retains the latest 550 days. SESC resolves the current-year page from its stable archive and retains enforcement, market-monitoring policy, and public-comment signals. JPX, TSE, and JSDA use structured current-year tables. PMDA retains only `安全` category rows from the latest 550 days. The Courts adapter is deliberately limited to the official recent Supreme Court filter (listed decisions from the past three months) and must never be described as comprehensive case-law coverage. Existing METI robustness and warning-only Source Health behavior remain unchanged. **JPO remains deferred** because its official update page is unstable for automation behind AWS WAF, while its available patent-data API is not an agency-news or regulatory-update feed; revisit only when a stable, focused official feed/API is available. Stage 1 does **fetch → normalize → de-duplicate → log** and nothing else.
- House of Representatives, e-Gov Law, PMDA, JSDA-results, Courts, and SESC records may carry a controlled `stage_hint`. Diet/e-Gov lifecycle changes and recurring PMDA date/title updates use an opt-in event identity without altering the official `source_url`; URL de-duplication remains unchanged for every other source. The Diet list supplies no per-bill submission date, so `published_at` stays empty rather than being guessed. e-Gov Law uses structured promulgation/enforcement metadata only. JPX and JSDA public-comment deadlines come only from their structured closing-date table fields.
- `data/raw_items.json` is the **accumulated source history**: re-runs only append genuinely new items, and it must never be trimmed.
- New raw items that are actually appended by the existing ID/source URL merge rules receive `first_seen_at` using the Asia/Tokyo service date. Do not backfill legacy items, overwrite an existing valid value, or replace invalid historical values silently. If source/merge behavior changes, update tests that prove `first_seen_at` preservation.
- Public-comment items store `comment_deadline` only from the e-Gov RSS exact fixed `受付締切日時` field, JPX's structured `募集終了日` table cell, or JSDA's structured `募集期間` end date. This is source-gated structured parsing, not general prose date extraction. Never infer a deadline from `published_at`, `first_seen_at`, `last_checked`, `effective_date`, or arbitrary summary text.
- **Untrusted input — do not trust `source_url`, `title_ja`, or `raw_summary`.** They come from third-party feeds. The script stores them verbatim (with light text normalization for readability), stores `source_url` unchanged, and never renders or executes any of them. Any downstream stage that renders these fields must escape them (see `docs/app.js`).
- De-duplicates by stable `id` and, for ordinary sources, by `source_url`; the three documented lifecycle/recurring adapters use event identity with URL de-duplication disabled. Re-running only appends genuinely new items (idempotent).
- A failing source is logged and skipped — it must never stop the whole run.
- `published_at` is left empty when a feed provides no date — **never guess or synthesize dates**.
- Does **not** touch `docs/data/legal_updates.json`. Mapping raw items into the published schema (and any summarization) is a separate, later stage.

## Source Health Monitor (`scripts/source_health.py`)

- Source health is based on **raw fetched/parsed item counts per configured source**, not on publication into `docs/data/legal_updates.json`. If a source fetches 10 raw items and Stage 2 excludes all 10 as noise, source fetch health is still healthy.
- `scripts/fetch_updates.py` writes `logs/source_fetch_report.json` after each run with `schema_version`, `started_at`, `finished_at`, `configured_source_count`, and per-source rows containing `source_key`, `source_name`, `source_url`, `status`, `fetched_count`, `new_count`, `latest_published_at`, `duration_ms`, `error_type`, and `error_message`.
- `data/source_health_state.json` stores only minimal streak state: `consecutive_zero_runs`, `consecutive_error_runs`, `last_status`, `last_problem_at`, and `last_recovered_at`. Do not add per-run checked timestamps or counts that would create daily diffs while health is unchanged.
- Health states: `success` with `fetched_count > 0` is healthy and resets streaks; `success` with `fetched_count == 0` is a zero-result warning and increments `consecutive_zero_runs`; `error` increments `consecutive_error_runs`.
- One-off and two-run zero/error cases are warnings only. The final gate fails only for report/schema problems, configured/report source mismatch, all 24 sources currently zero/error, or one **gate-required** source reaching 3 consecutive zero-result or error runs.
- **Warning-only (non-gating) sources** (`gate_required=False` in `fetch_updates.SOURCES`, e.g. METI) are still fetched, reported, and have their streak state updated, but their 3-run streaks never fail the gate — `gate_warnings()` surfaces them as `::warning::` annotations / Step Summary notes instead (`gate_failures()` skips them). This is **not** a blanket gate weakening: every other source stays gate-required, the all-sources-failed fatal condition still fails, and report/state validation is unchanged. Mark a source warning-only only when its host is chronically flaky and its absence is tolerable for triage.
- In GitHub Actions, `source_health.py evaluate` must run after fetch and before build/summarize; `source_health.py gate` must run after the commit step so other source updates and health-state changes can be committed first. Scheduled runs (`github.event_name == 'schedule'`) persist state and enforce 3-run streak gates. Manual `workflow_dispatch` runs still generate reports, Step Summary, and warnings, but must not increment/reset persistent streaks and must not fail solely because an existing streak has reached 3. If a new configured source is absent from the previous state file, the manual gate may add only its default state in memory; malformed or unknown state remains fatal.
- Raw fetch should retry only transient fetch failures (timeouts, connection errors, HTTP 429, HTTP 5xx) with a small capped retry budget. Do not retry permanent 4xx errors and do not log response bodies, secrets, or environment values.
- The monitor is administrator-facing only. Do not modify `docs/app.js`, `docs/index.html`, `docs/style.css`, public cards, CSV export, URL state, or dashboard Data status for Source Health.
- When adding a source, add a stable `key` to `fetch_updates.py`, keep `source_name`, ID generation, and `source_url` behavior unchanged, add an English display name in `source_health.py`, and update source-health tests. Check the GitHub Actions run Summary tab for the generated Source Health table.

## Provisional public data (`scripts/build_public_data.py`)

- Maps `data/raw_items.json` → `docs/data/legal_updates.json` (the published file), backing up the previous file to `docs/data/legal_updates.backup.json` first.
- **Interim, rule-based, pre-AI stage. It does NOT provide official translation, summarization, or legal/business judgement.** `title_en` is a conservative rule-based English label for triage; `summary_en` / `business_impact_en` / `recommended_action_en` are FIXED template sentences that tell the reader to check the official Japanese source. Never present this output as analysis.
- `area` / `stage` / `impact_level` come from simple keyword rules over controlled vocabularies. Conservative by design: `impact_level` is only `Low` or `Medium` here — `High` is reserved for a later evidence-based (AI/human) stage.
- **Ranking is a technical heuristic, NOT a legal judgement.** Items are scored by an internal keyword `relevance_score` (boosts law-reform / regulation / public-comment / guideline keywords; penalises minutes, statistics, web magazines, bare page updates; e-Gov public comments get a source bonus) and ordered by `relevance_score` → impact weight (Medium > Low) → recency (light penalty for old items). It only decides *what to surface*, never legal importance. The score is written as an optional `relevance_score` field (the UI ignores it).
- Public-comment stages distinguish `Public Comment Open`, `Public Comment Closed`, and `Public Comment Results Published`. An otherwise Open item becomes Closed at a valid structured `comment_deadline`; date-only values remain Open through 23:59:59 JST, while explicit date-times respect their offset. Stage 2 may inherit a trusted e-Gov deadline for a duplicate official-source record only when the conservative normalized title is exact, publication dates are within one day, the e-Gov contact agency matches the target's configured source name and official domain, both sides are one-to-one, the target has no deadline, and no deadline conflict exists. Never use fuzzy title similarity or write inherited deadlines back to raw history. Missing, invalid, ambiguous, or conflicting deadlines leave the stage unchanged; inherited public fields retain auditable source metadata. Closed public comments are retained as useful regulatory history but slightly demoted in ranking so open consultations and draft guidelines generally rank higher; strong legal/regulatory signals can soften that demotion.
- METI / CAA source expansion uses additional title keyword rules for provisional area classification, including economic security / FDI, energy / environment, data / privacy / AI, antitrust / fair trade, consumer / advertising, and corporate governance. These labels remain triage metadata, not legal conclusions.
- PPC / JFTC source expansion uses additional keyword rules: PPC items are biased toward `Data / Privacy / AI`, and JFTC items are biased toward `Antitrust / Fair Trade`. Committee meetings, recruitment, procurement, events, and public-relations-only updates should be excluded or heavily downranked unless strong legal/regulatory keywords are present.
- MLIT / MAFF source expansion uses additional keyword rules: MLIT covers land, infrastructure, transport, construction, real estate, logistics, and related regulatory updates; MAFF covers food, agriculture, forestry, fisheries, quarantine, import/export, and related regulatory updates. New sources can add noise, so ranking and exclusion rules intentionally filter out events, procurement, hiring, statistics-only items, and general publicity.
- Additional public-comment area rules classify clear healthcare/pharma, food/agriculture, transport/infrastructure, real-estate/land-use, and public-safety/disaster-management signals so `Other` is reserved for genuinely unclear items.
- Excludes clear administrative noise and items with no net legal/regulatory signal — unless a strong keyword rescues them; public comments are always kept. Ministry-source noise (recruitment, procurement, events, bare meeting/committee announcements, exams, market data, speeches, subsidy adoptions/calls, web magazines, statistics-only, white-paper-only, kids/PR pages) is excluded or heavily downranked.
- **Keeps the canonical published dataset uncapped** (`DEFAULT_OUTPUT_LIMIT = 0`); a positive `--limit` is diagnostic-only. The raw history also remains cumulative. `build_public_archives.py` runs after summarize/translate and writes an uncapped shard for each valid publication year plus an `undated` shard and timestamp-free manifest. Unknown/invalid dates rank last and go to `undated`. Keeps `source_url` verbatim; input is untrusted (the UI escapes on render).
- MOJ / MOE / MOF / MIC / MLIT / MAFF area rules are source-gated like METI/CAA/PPC/JFTC (MOJ → corporate/registry/civil-law/immigration/AML; MOE → environment/waste/chemicals, disaster items to Public Safety; MOF → FX/FDI/customs/tax to Finance or Economic Security; MIC → telecom/spectrum/broadcast/digital-administration to Data / Privacy / AI; MLIT → land/infrastructure/transport/real estate/disaster; MAFF → food/agriculture/forestry/fisheries/quarantine). MIC deliberately has **no** source fallback — unmatched items stay `Other`.
- If the previous published file contains `summary_source: "claude"` for the same `id` and unchanged `source_url`, Stage 2 preserves the Claude summary fields while refreshing build-owned metadata such as `area`, `stage`, `impact_level`, `relevance_score`, titles, source, and dates.
- Stage 2 passes through only valid non-future `first_seen_at` values in strict `YYYY-MM-DD` form. Missing, null, invalid, or future values are omitted from the public JSON rather than written as `null`.
- Stage 3 may replace the template English fields for selected top-ranked records, but the keyword-derived `area` / `stage` / `impact_level` labels remain preliminary triage metadata unless a later reviewed process changes them. Keep the output escaping and the disclaimer intact.

## AI summarization (`scripts/summarize_updates.py`)

- Stage 3 reads `docs/data/legal_updates.json` and optionally uses the Claude API to summarize published items. By default it considers the top `--limit` items by `relevance_score` (default 10); explicit `--all-items --english-only` and `--all-items --japanese-only` modes provide resumable language-specific full-corpus maintenance while preserving the other language, and the daily workflow runs both (see the daily call budgets below). `--api-limit` caps cache-miss API calls; cache hits are free, and existing complete summaries are cache hits. A fatal provider error warns without stopping the remaining legal-data pipeline. It must be run explicitly with `ANTHROPIC_API_KEY`; do not assume the published file has AI summaries unless the corresponding English or Japanese provenance fields show that it has been processed.
- Stage 3 normally produces canonical English fields first. For a later cache hit that lacks Japanese fields, it uses one call from the same `--api-limit` budget to generate `summary_ja`, `business_impact_ja`, and `recommended_action_ja` directly from Japanese `title_ja` / `raw_summary`. `--all-items --japanese-only` is the explicit resumable full-corpus path: it generates only those Japanese fields, preserves the English body and its `summary_source`, and records separate Japanese provenance. It must not translate `summary_en`, generate a replacement title, or change `title_ja`.
- **Japanese backfill workflow + concurrency.** `.github/workflows/japanese-summary-backfill.yml` is a manual, checkpointed, Japanese-summary-only path. It processes missing summaries with bounded parallel direct calls, commits each successful round to the dispatched branch, rebuilds yearly archives, and finishes only when every published item passes its Japanese provenance/content gate. It never fetches, runs Stage 2, translates English, or touches source health. It shares `concurrency.group: japan-legal-reform-data-writer` with other data-writing workflows. Never recover an old index-addressed Message Batch after corpus coverage has changed; its positional results can no longer be mapped safely.
- **English backfill workflow + dependent translation refresh.** `.github/workflows/english-summary-backfill.yml` is a manual, checkpointed `--all-items --english-only` path with bounded parallel direct calls and separate measured caps for summarization and the dependent zh-Hans translation refresh. The selected parallelism applies to both phases. Japanese fields are hashed before/after and must remain identical. Because changing canonical English (including restoration of an existing cached AI title after Stage 2) invalidates the Stage 4 source hash, every checkpoint scans and refreshes all affected zh-Hans candidates before it can publish; the translation dollar cap, not the English batch size, bounds that dependent phase, and Chinese coverage may not shrink. If translation fails after successful English calls, the workflow restores the public file and translation cache to `HEAD`, commits only the new English summary cache responses, and fails the run; a funded rerun can then restore those English results as free cache hits without publishing stale Chinese. A successful checkpoint commits summary/translation caches plus public/archive data, requests Pages, and passes its final gate only when all English summaries and current Chinese translations are complete. It never fetches, runs Stage 2, or touches source health, and shares the data-writer concurrency group.
- API keys are read only from `ANTHROPIC_API_KEY`. Do not write API keys to code, README examples with real values, logs, cache files, or generated JSON. The summary model is **`claude-sonnet-5-5`** (code default and every summary workflow) and can be changed with `--model` or `ANTHROPIC_SUMMARY_MODEL` (legacy `ANTHROPIC_MODEL` remains a lower-priority fallback).
- **`model_pricing()` matches the LONGEST prefix, and an unpriced model returns None.** A model id can be a prefix of its own successor — `claude-opus-5-5` starts with `claude-opus-5` — so first-match-in-table-order priced it at $5/$25 instead of its own $4/$20, silently, and 25% wrong in both the cost report and the pre-flight bound that decides trimming. Order-independence is the point: ordering the dict by hand also works until someone appends a row. Cache **write** rates are derived (5m = 1.25x input, 1h = 2x input) and a test checks every row; cache **read** is quoted per model and must be copied, not derived — Opus 5.5 is $0.20 against a $4 input, where 0.1x would be $0.40.
- **Stage 3 moved from `claude-opus-4-8` to `claude-sonnet-5-5` on 2026-09-30, on measured evidence.** `summary-model-eval.yml` ran both over the hard (30) and stratified (24) frozen sets in English and Japanese: zero schema failures, refusals, or guardrail violations on either; Sonnet cost 42% (English) and 45% (Japanese) per item despite 10-23% more output tokens; on reading every output it was as accurate or more so (it scoped impact correctly when the amended order only concerned public servants, and stated draft status consistently). Its blemishes were rare — one garbled phrase, one odd parenthetical, one correct but unsourced gloss, URLs pasted into Japanese text, and longer titles. The summary cache key does not include the model, so existing Opus summaries stay published; only new or changed items are written by Sonnet, and the `summary_model` field records which. Reverting is the same env change in the four workflow lines. The title prompt now asks for at most 110 characters, because titles over `TITLE_MAX_CHARS` (120) are cut mid-title and 63% (Opus) / 83% (Sonnet) of hard-set titles were.
- **`claude-opus-5-5` is priced in the table but NOT adopted.** Switching to it is env-only and reversible, but it is not a drop-in: Opus 4.8 runs without thinking when `thinking` is omitted, which is what this script does, while Opus 5.5 **cannot disable thinking at all** (`{"type": "disabled"}` and `budget_tokens` both 400 at every effort level) and defaults to `medium` effort. Thinking tokens bill as output, so a 20% lower per-token price can still cost more per call. Measure with `scripts/evaluate_summary_model.py` — quality AND actual output tokens, across effort levels — before changing `ANTHROPIC_SUMMARY_MODEL`.
- **The thinking setting is per model and comes from `anthropic_batch.lowest_thinking_config()`; never write a `thinking` literal in a stage.** Every Claude call here is rendering into a fixed JSON schema, so each asks for the least thinking its model accepts: `{"type": "disabled"}` on Opus 4.8 / Sonnet 5 / Haiku 4.5 (identical to the old omitted field on Opus 4.8), `{"type": "between_tools"}` on **Sonnet 5.5**, and omitted on Opus 5.5 / Fable, which cannot turn it off. Sonnet 5.5 returns 400 for `disabled` and runs adaptive thinking at `high` effort when the field is omitted, so an env-only switch would either fail every call (a green job in warn mode) or bill thinking on every call. `between_tools` accepts no other field and effort `high` or below; the stages leave effort at the API default (`high`). A `stop_reason: "refusal"` raises `ModelRefusal`, is classified `refusal` (non-fatal: the item keeps its fallback), and is reported as `refused_items` in each stage summary; `evaluate_summary_model.py compare` treats a higher refusal rate as a blocker.
- `summary_source` semantics: Stage 3 AI-summarized items get `summary_source: "claude"`; items not summarized or failed in the Stage 3 run get `summary_source: "rule_based"`. Before Stage 3 has ever run, `summary_source` may be absent from Stage 2-only output.
- UI transparency: cards show `AI Summary` for `summary_source: "claude"` and `Rule-based Preview` for `summary_source: "rule_based"` or missing values. `AI Summary` is still unofficial and not legal advice; `Rule-based Preview` is an AI-pre-summarization placeholder. The results status line reports locale-specific content coverage (English AI summaries, Japanese-source AI summaries, or complete Simplified-Chinese translations) and latest `last_checked` over the full filtered set.
- `docs/data/legal_updates.before_ai.json` is an initial pre-AI baseline created once on the first non-dry-run Stage 3 execution. It is not a per-run timestamped backup. Stage 2 continues to use `docs/data/legal_updates.backup.json` for the previous generated public file.
- Guardrails are load-bearing: do not invent facts; do not provide legal advice; do not state that a law has been enacted, promulgated, or entered into force unless the provided source text clearly supports it; clearly label public comments, drafts, proposals, consultations, draft guidelines, and government announcements; treat Japanese official sources as authoritative. `area`, `stage`, and `impact_level` are preliminary rule-based labels, not legally verified conclusions.
- Stage 3 logs obvious definitive/legal-advice wording as caution warnings for review. These warnings are not a substitute for human or qualified legal review.
- Stage 3 must preserve `first_seen_at` if present and must not add it to legacy items during summarization.

## AI translation (`scripts/translate_updates.py`)

- **Stage 4, optional.** Reads `docs/data/legal_updates.json` and `data/translation_cache.json`, and adds an unofficial Simplified-Chinese (`zh-Hans`) translation under each item's `translations.zh-Hans`. It does not generate Japanese; Japanese card text comes from the Stage 3 `*_ja` summaries. English stays canonical; the Japanese official source remains authoritative. Run after Stage 3 so it translates the final English (AI where available, rule-based otherwise). Never run the real API locally unless explicitly asked and `ANTHROPIC_API_KEY` is set.
- **Only translates** `title_en` / `summary_en` / `business_impact_en` / `recommended_action_en` → `translations.zh-Hans.{title,summary,business_impact,recommended_action}`. It must **never** modify `id`, `title_ja`, `source_name`, `source_url`, `area`, `stage`, `impact_level`, `published_at`, `last_checked`, `first_seen_at`, `comment_deadline`, its provenance fields (`comment_deadline_source`, `comment_deadline_source_id`, `comment_deadline_inherited`), `relevance_score`, or any summary metadata (`summary_source`, `confidence`, `ai_notes`, …).
- **A rejected title is remembered, so it is not bought again every day.** A rejection is deliberately never cached as a translation, so the item was a cache miss on the next run, was translated again, was rejected again, and the loop only ended when the English itself changed — one item repeated that cycle for five consecutive days. `cache["rejected"][locale][item_id]` (schema_version 3) now records `source_hash`, `prompt_version`, an `attempts` count and the structural `reasons` — never translation text, same rule as the logs. After `MAX_TITLE_ATTEMPTS` runs the item is **parked**: it is reported as `quality_parked_items`, keeps its English fallback, and costs nothing until its English changes, which clears the record automatically because the record is keyed on `source_hash`. Parking stops the spend, not the accuracy rule — a translation of superseded English still comes off the card. Dead records are pruned each run (`rejections_pruned`).
- **Translation cache** `data/translation_cache.json` is `{ "schema_version": 3, "entries": { "zh-Hans": { "<item-id>": { source_hash, prompt_version, translated_at, model, title, summary, business_impact, recommended_action } } } }`. The item id is the outer key. `source_hash` = SHA-256 over `locale | prompt_version | title_en | summary_en | business_impact_en | recommended_action_en | title_ja | stage | source_name` (id is NOT hashed). A cache entry is adopted only when its `source_hash` **and** `prompt_version` still match and the cached translation is valid; otherwise it is a cache miss — so a change to the Japanese original name, the stage, or the source also re-translates. Cache hits do not rewrite `translated_at` (no needless diffs). Bump `PROMPT_VERSION` (or the in-code glossary) to invalidate every translation.
- **Field-level memoization (`fields` section, schema_version 2).** Beside `entries`, the cache carries `fields[locale][<field-hash>] = { field, text, prompt_version, translated_at, model }`. The field hash is SHA-256 over `locale | prompt_version | field | english_text`, plus `title_ja | stage | source_name` **for the `title` field only**. Rationale: every not-yet-AI-summarized item shares one identical set of rule-based `summary_en` / `business_impact_en` / `recommended_action_en` sentences, so keying those on the English text collapses hundreds of paid translations into one and makes the boilerplate render identically on every card; the title genuinely varies with its Japanese original (prompt v3 sends `title_ja` so Japan-specific statute names survive), so it keeps that context in its key and must NOT be deduplicated on English text alone. A run requests only the fields that miss the field cache — `max_tokens` shrinks with the subset — and skips the API entirely when all four hit (that free assembly does not consume `--limit`). The field cache is seeded once from existing `entries` whose `source_hash` is still current, so the upgrade costs no API calls; seeding picks the most frequent cached rendering, breaking ties on the smallest text, so it is deterministic. The `system` prompt is identical for every field subset, so the prompt cache keeps hitting.
- **Batch recovery is provider-side, not file-based.** A Message Batch keeps running and billing after the caller dies, and on GitHub Actions the runner's filesystem dies with it — the daily workflow commits only at the very end, so a batch id written to a local file is gone on the next run. Every batch request therefore carries a **self-describing `custom_id`** (`{kind}-{item_id}-{source_hash12}-{mask}`; kinds `t` translate, `se`/`sj` summarize English/Japanese). The next run lists recent batches server-side, reads those ids off the results, and applies anything already paid for — with **no local state at all**. A result is applied only when the item's CURRENT hash still matches the one in its id, so nothing generated from superseded source content is published; re-collecting an already-applied batch is a no-op. Results stay retrievable for 29 days.
- **Phase 3A: `daily-update.yml` runs all three Claude stages as Message Batches** (50% discount; same model, same prompts, so no quality change). `--parallel` is rejected with `--batch` and was removed from those steps; `--max-cost-usd` is kept and now enforced as a pre-flight bound (current values under the daily call budgets). The job carries an explicit `timeout-minutes: 300` because three stages can each wait an hour. **The backfill workflows deliberately stay on direct calls** so a Batch problem is easy to isolate; dropping `--batch` restores the direct path with no other edit. Each stage prints `batch_id`, submitted/recovered counts, interlock state, succeeded/errored/expired/canceled/missing, token and cache counts, the pre-flight estimate, the measured cost, field-cache hits, and duration into the Step Summary.
- **`atomic_replace()` retries a transient Windows file lock.** `os.replace` is atomic, but an on-access scanner can hold a freshly written temp file for milliseconds, which was failing roughly four offline test runs in five and could abort a local pipeline write. Every pipeline writer goes through it; a genuine permission error still surfaces after the last attempt. CI (Linux) never takes this path.
- **Submission interlock: never submit while a batch is running.** `batches.list()` exposes ids and statuses, but `custom_id`s are only readable once a batch has ENDED — so an in-flight batch cannot be attributed to us. A rerun minutes after a lost runner would see it, fail to recognise it, and resubmit the same work. Batch mode therefore refuses to submit while ANY batch in the API key's workspace is `in_progress` or `canceling`. This is precise on a workspace dedicated to this pipeline (recommended) and merely conservative on a shared one; `--no-batch-interlock` opts out and accepts the duplicate-spend risk.
- **Discovery failure is fatal in batch mode.** `list_recent_batches()` raises `BatchDiscoveryUnavailable` rather than returning an empty list, because "no batches" and "cannot see batches" must not be conflated. Without the list there is neither recovery nor interlock, so the run declines to submit instead of risking a second charge for work already in flight.
- **`data/reviewed_field_translations.json` holds human-checked field text.** A seeded canonical string is only the most frequent machine rendering that passed the automatic gate, yet one such string appears on ~1,700 cards. An entry here (keyed by field hash) is pinned with `reviewed: true`, overrides seeding, is pushed onto already-published items for free, and stops applying the moment the English text changes — a new hash needs new review rather than inheriting an old approval. `--show-shared-fields` lists what is worth reading.
- **A local polling timeout does NOT cancel the batch.** Anthropic runs a batch for up to 24 hours; cancelling because our own wait expired would discard requests that are already complete and already billed. The wait simply stops and the next run collects it (`cancel_on_timeout=True` restores the old behaviour). `canceling` is treated as a live status, not a terminal one.
- **Output is budgeted at a calibrated size, not at the `max_tokens` ceiling.** `MAX_TOKENS = 1500` stays the hard per-response limit, but pricing every pre-flight request at it made the bound a true upper limit and a useless one: measured output is 466 tokens/call (English), 296 (Japanese) and 248 (zh-Hans), with a corpus maximum of 427, so ~80% of the bound was headroom that is never used. A 30-call run was silently trimmed to 22 while real spend sat at 43% of the cap, and Japanese/Chinese coverage of the newest items fell behind. Both scripts now budget at `EXPECTED_OUTPUT_TOKENS = 700` (~1.6x the largest output ever seen, under half the ceiling) and report `preflight_ceiling_usd` beside `preflight_cost_usd` so the true worst case (`api_limit x MAX_TOKENS`) stays visible rather than implied. This is a scheduling estimate, not a guarantee.
- **Daily call budgets are sized against measured arrival.** New items arrive at ~38/day (601 over 16 days, single days above 70). The daily workflow runs English at `--api-limit 80 --max-cost-usd 1.10`, Japanese at `--api-limit 50 --max-cost-usd 0.80`, and zh-Hans at `--limit 140 --max-cost-usd 1.30`. English is the only stage with a real backlog (1,709 items on 2026-09-09), and at 50 it barely outpaced arrivals — one run summarized 50 while `english_remaining` still rose, because 70 items arrived that day. Japanese stays at 50 because it is generated from the Japanese source metadata directly, so its demand is arrivals only and it reached 99% coverage there. zh-Hans moved to 140 only because English moved to 80: every English upgrade invalidates that item's Chinese translation, so its demand is arrivals plus the English limit, less the overlap. zh-Hans is deliberately the largest budget because its demand is roughly double a summary stage's: new arrivals PLUS re-translation of every item the summary step just upgraded to an AI English summary. At 60 it was still losing ground (279 candidates, `skipped_no_budget: 219`, untranslated 212 -> 221 in one day). Its cap looks generous against ~$0.34 measured spend because the pre-flight bound prices the entire `count_tokens` result at the full input rate while ~70% of this stage's prompt is served from the cache at 0.1x (estimated $0.426 vs $0.172 billed); pricing cache reads correctly would let the cap come back down. Tests pin the invariant that each stage's cap can actually pay for its own call limit, because those two numbers are set independently and nothing previously linked them. **Which of the two is binding is worth checking before changing either.** `cost_budget_skipped` counts work deferred by the USD cap and `skipped_no_budget` counts work deferred by the call limit; on zh-Hans the first has been 0 on every run measured, so raising its cap changes nothing on its own. Per-request cost there is flat at ~$0.0070 (+/-2%), so the pre-flight bound sits near $0.98 at `--limit 140` regardless of backlog size.
- **`--batch` and `--max-cost-usd` now coexist.** Batch usage is only known after completion, so the measured cap could never fire and the two flags used to be mutually exclusive — which meant enabling `--batch` silently removed the only spend brake. Batch mode now bounds spend **before** submitting: `count_tokens` per request (free), multiplied by a safety margin because Anthropic documents it as an estimate, plus the full `max_tokens` ceiling for output, times the 0.5 batch discount. Requests that do not fit are deferred to the next run. This is a conservative bound, not a guarantee — highly parallel batch processing can overshoot a configured limit slightly.
- **Measured cost guard for direct calls.** Successful API responses report base input, output, prompt-cache creation, and prompt-cache read tokens. In direct-call mode `--max-cost-usd` stops scheduling once the measured conservative estimate reaches the cap: sequential mode may overshoot by one response, and a bounded `--parallel N` wave (N from 1 to 10, never combined with `--batch`) by at most `N-1` more. A capped run rejects an unpriced model instead of pretending the cap is enforceable, and provider billing remains authoritative. The manual translation backfill defaults to a USD 0.50 cap; the daily caps are listed under the daily call budgets.
- **Seeded canonical field text is NOT human-verified.** It is the most frequent machine-generated rendering that passed the automatic quality gate. `--show-shared-fields` lists the translations reused across many items (the three rule-based sentences each stand in for ~1,700 cards) so a person can read them; adding `"reviewed": true` to an entry pins it against re-seeding until the English itself changes.
- **In-flight batch record (`pending_batch`).** A Message Batch keeps running and billing after the caller dies. `--batch` writes `pending_batch[locale] = { batch_id, model, prompt_version, submitted_at, requests }` to the cache file **before** waiting, and the next run reclaims those results instead of resubmitting; a translation is only applied when the item's current `source_hash` still matches what was submitted. The record is cleared once results are in hand, and a second batch is never submitted while one is outstanding.
- **`--limit N` (default 30) bounds NEW API calls per run, not items inspected.** The script scans the published file in order; cache hits and valid translations are free and do not consume the limit, so successive daily runs translate the whole corpus incrementally. The first bulk translation of the full corpus is a separate, deliberate operation (raise `--limit` once, off the daily schedule).
- **Stale removal:** on each run the script recomputes `source_hash` from the current English, re-applies only valid cached/fresh translations, and **removes** any `translations.<locale>` block that no longer matches (e.g. after the English upgraded from rule-based to Claude). Stage 2 may carry translations forward across rebuilds, but Stage 4 is authoritative and prunes stale ones.
- **Model precedence:** translation resolves the model as `--model` > `ANTHROPIC_TRANSLATION_MODEL` > `DEFAULT_TRANSLATION_MODEL` (the code default `claude-haiku-4-5-20251001`; `ANTHROPIC_MODEL` is **not** consulted for translation). **Every workflow that translates (daily, translation backfill, English summary backfill) sets `ANTHROPIC_TRANSLATION_MODEL=claude-sonnet-5` on its translate step only**, so zh-Hans translation runs on Sonnet 5 while summarization runs on Sonnet 5.5 (`summarize_updates.py` default `claude-sonnet-5-5`); the translation code default is unchanged and the switch is env-only and reversible. The selected model is printed in the run summary and stored in each new cache entry's `model`, but it is **not** part of `source_hash`, so switching the model does not invalidate the cache — existing entries are kept and only new/changed items are re-translated (no `PROMPT_VERSION` bump). The translate call passes the model's lowest thinking setting — `{"type": "disabled"}` on Sonnet 5, `{"type": "between_tools"}` on Sonnet 5.5 (translation is faithful rendering, not reasoning; this also prevents Sonnet 5's default adaptive thinking from truncating the JSON at `MAX_TOKENS`) and sends no `temperature`/`top_p`/`top_k`. API keys come only from `ANTHROPIC_API_KEY`; never write keys to code, logs, caches, or JSON.
- **`--no-api` / missing key:** apply only valid cached translations, remove stale ones, and exit 0 — never call the API. On any per-item API/validation failure, keep the English fallback (no translation), log it, and continue; failures never abort the run.
- **Save-integrity instrumentation + gate.** `translated_items` counts only translations that are applied to the published item AND written to the cache (not mere API responses). The run computes semantic before/after diffs (`new/updated/removed_cache_entries`, `published_added/updated/removed`), re-reads the saved files to confirm they hold the in-memory state, logs per-candidate diagnostics (`candidate_reason` = missing_cache / hash_mismatch / invalid_cache / invalid_title, plus had_published_translation / cache_present / cache_prompt_version / hash_match — never any translation text or secrets), and **exits 1** if `translated_items > 0` produced no new/updated cache or published entries, if the cache shrank, or if the saved file counts disagree with the in-memory counts. This turns a silent "success but nothing persisted" into a loud failure.
- **Provider error classification + fail-fast.** `classify_provider_error()` maps Anthropic exceptions (by type + HTTP status, then a narrow billing signal) to `insufficient_credit` / `authentication_error` / `permission_error` / `rate_limit` / `temporary_server_error` / `network_error` / `unknown_provider_error`; non-API parse/field problems are `item_validation_error`. The three **fatal** types (`insufficient_credit`, `authentication_error`, `permission_error`) do not recover within a run, so on the **first** occurrence the script stops calling the API and marks the rest `provider_aborted_items` / `api_calls_avoided` instead of repeating the same failure (no `failed_items: 30`). A timeout/network failure of an entire optional Message Batch is also one provider-wide failure: it must set `provider_status: unavailable`, retain the submitted-call count, emit one provider marker, and must not claim the provider is healthy or log one error per item. Error bodies, request ids, API keys, and source/translation text are **never** logged — only the safe type and a single `PROVIDER unavailable type=…` line. `--provider-failure-mode` (env `TRANSLATE_PROVIDER_FAILURE_MODE`, default `fail`) selects behavior: **`warn`** (daily) exits 0 so fetch/build/summarize/commit continue and a `::warning::Translation provider unavailable: <type>` annotation is surfaced; **`fail`** (backfill) exits 1 so the run fails before any commit. A provider outage with `translated_items == 0` is reported as `provider_status: unavailable` (not an integrity-gate failure), so warn mode never trips the save-integrity gate. Stale-translation removal is unchanged: a translation of changed Japanese source is dropped (English fallback) even during an outage — legal accuracy over completeness — and the item stays a re-translation candidate once the API recovers.
- **Backfill workflow + concurrency.** `.github/workflows/translation-backfill.yml` is a manual (`workflow_dispatch`) **zh-Hans translate-only** path that uses bounded direct calls, so one delayed Message Batch cannot withhold the whole checkpoint: checkout → setup → install → compile translator/archive builder → offline tests → count-before → `translate_updates.py --locale zh-Hans --limit 30` → count-after → semantic integrity gate → rebuild yearly archives → pre-push sync check → commit translation cache, canonical JSON, manifest, and shards → request a Pages build from the latest `main` revision. The gate requires non-shrinking artifacts and verifies that every published translation matches a valid current-hash cache entry; cache-only stale/history entries are allowed because a source-hash change invalidates publication without requiring destructive cache cleanup. It never fetches, runs Stage 2, summarizes, or touches source-health/raw/summary state, so the corpus accumulates without the daily build regenerating the published file underneath it. Its disabled-by-default `omit_title_ja_reference` input is a bounded recovery mode for an item repeatedly rejected because the model copies Japanese kana: the API receives the canonical English target fields with an empty reference title, while the stored `title_ja`, cache hash inputs, and normal daily behavior remain unchanged. It and every other data-writing workflow (daily, Japanese and English summary backfills) share `concurrency.group: japan-legal-reform-data-writer` (`cancel-in-progress: false`) so they never write concurrently; the backfill aborts (no rebase/force) if `origin/main` advanced since checkout.
- **Prompt version `zh-hans-v3`** (in `PROMPT_VERSION`). v3 keeps the v2 title formatting rules (short, complete, scannable per stage: `公开征求意见：…`, `（已结束）公开征求意见：…`, `公开征求意见结果：…`, `指南草案：…`, `法案提交：…`; `公开征求意见` once; no ellipsis/truncation; body-field caution `可能`/`视…而定`, `建议考虑…`). It adds: (1) the Japanese **reference context** `title_ja` / `stage` / `source_name` is sent to the model **for reference only** (translate-target stays the four English fields; the model must not translate or return the reference, any Japanese name used in the returned title must be rendered fully in Simplified Chinese with no copied kana, and `apply` only ever writes the four fields); (2) priority when the English and `title_ja` differ — formal Japanese statute/system name in `title_ja` > English meaning > Chinese brevity, adding no legal effect/obligation/deadline/penalty; keep Japan-specific names (`特定外来生物`, `育成就労`) rather than generalizing, wrap statute names in `《》`, and keep 法/政令/省令/施行令/施行规则/告示 distinct; (3) numeric dates rendered `YYYY-MM-DD`. Bumping the version makes every older cache entry a cache miss; clarifying the instructions without changing the output contract does not bump it, so already validated entries stay valid.
- **Translation validation:** the four fields must be non-empty strings with no HTML tags or Markdown code fences and within length caps (title ≤ 90, summary ≤ 800, business_impact ≤ 500, recommended_action ≤ 500). Over-limit output is rejected (not truncated) and not cached. A dedicated **Chinese title quality check** additionally rejects titles that are empty/over 90 chars, contain `...`/`…`, contain Japanese kana, repeat a stage phrase or a word/fragment (e.g. `规则、则`, `修订修订`), have duplicated punctuation, unbalanced `《》`/`（）`/`()`, or line breaks — detection is conservative to avoid false positives on legitimate Chinese. The title check also rejects a small, exact set of **known mistranslated statute names** (`外来入侵物种法`, `开发与雇佣适当实施及保护法`) — title-only, so legitimate body text is unaffected. If the **title** is rejected the whole item's translation is dropped (English fallback), not cached, and counted as `quality_rejected_items` (not `failed_items`); processing continues. **A rejected title gets one recovery call** when `--retry-rejected-title-without-ja-reference` is set (the daily workflow and the English summary backfill set it; `--retry-kana-title-without-ja-reference` is the original spelling and still works): the item is re-requested once with `title_ja` blanked, because that reference is what carries kana and Japanese phrasing into the Chinese title — both the kana leaks and the doubled words the gate catches (`特性試験の試験方法` rendering as `试验试验`) come from following it too closely. The retry weakens no check; whatever comes back faces the same gate. In batch mode the retry is a direct follow-up call capped at `MAX_TITLE_RETRIES_PER_RUN`, because a batch cannot retry within itself and a second batch would mean another hour's wait for a handful of items. After validation and **before** the title gate, two deterministic normalizations run over the four translated fields only. **Date normalization** converts `YYYY/MM/DD` and `YYYY.MM.DD` to `YYYY-MM-DD` (ambiguous `MM/DD/YYYY`, metadata dates, `title_ja`, and `source_url` are untouched). **Name-separator normalization** converts the Japanese separator `・` (U+30FB) and its half-width form `･` (U+FF65) to the Chinese interpunct `·` (U+00B7). That separator is punctuation, not kana — it carries no Japanese reading and every accepted translation in the corpus already uses `·` — but it lives inside the katakana Unicode block, so the kana gate rejected correct renderings of any institution name built with it (`農業・食品産業技術総合研究機構`, `水産研究・教育機構`). Nine of the ten titles rejected on 2026-09-07 carried it in their Japanese original against a 12.3% corpus base rate, and because a rejection is never cached each one was re-translated and re-rejected on every later run. Normalizing runs before the gate so a title is judged on the text that will actually be published; it is exactly one codepoint pair, and hiragana, katakana letters, the prolonged sound mark `ー`, and the kana iteration marks still reject the title. Prompt guardrails: translate faithfully only; add no obligations/deadlines/penalties/scope absent from the English; no legal advice; do not map Japanese legal concepts onto Chinese-law concepts; preserve numbers, dates, institution and statute names; Simplified Chinese only; JSON only.
- **UI transparency:** in `zh-Hans` mode a card with a translation shows a subtle `AI翻译` badge and the note "本译文由AI生成，仅用于信息监测。应以日文原文为准。"; a card without one shows "中文翻译暂不可用，以下显示英文。" and English text. Japanese mode shows no translation badge: it uses `title_ja` for the title and the Stage 3 `*_ja` summaries with a note that they were summarized directly from the Japanese source metadata, falling back to English with a notice while they are absent. All translated and summarized values still pass `escapeHtml()`, and `source_url` still passes `safeUrl()`.

## Disclaimer modal

- The modal is shown on first visit and on any visit where `localStorage` key `jlrw_disclaimer_accepted_v1` is missing.
- Acceptance is stored as an ISO timestamp under that key.
- The modal must always link to the full disclaimer page `docs/legal/disclaimer_en.html` (generated from `legal/DISCLAIMER_EN.md`).
- The footer must always link to both published disclaimer pages (`docs/legal/disclaimer_en.html` and `docs/legal/disclaimer_ja.html`).
- The `legal/*.md` files remain the canonical source of the disclaimer text; keep the published HTML pages in sync with them and do not weaken the disclaimer language.
- Do not silently remove, weaken, or auto-dismiss the modal.

## What NOT to do

- Do not phrase summaries as advice or as definitive interpretations of Japanese law.
- Do not describe `Newly detected` items as new laws, new regulations, recently enacted, recently amended, or breaking legal updates.
- Do not silently drop the disclaimer modal or weaken its language.
- Do not introduce external runtime dependencies without explicit approval.
- Raw fetch, the **provisional** rule-based build, the optional Stage 3 English/Japanese summarization script, the optional Stage 4 zh-Hans translation script, and the existing daily update workflow are in scope. Do **not** run the real Claude API locally unless the user explicitly asks and `ANTHROPIC_API_KEY` is set. Do not add broader GitHub Actions automation until explicitly requested. Never present template English copy or AI output (summaries or translations) as official, certified, comprehensive, or legal advice; keep rule-based `impact_level` conservative (no rule-based `High`).
- Do not let Stage 4 modify English canonical fields, Japanese Stage 3 summary fields, or any non-translatable metadata; do not write empty `translations` blocks or `translations.ja`; and do not present `zh-Hans` translations or Japanese AI summaries as official. English is canonical and the Japanese official source is authoritative.
- Do not expose Source Health Monitor data in the public UI; it is limited to GitHub Actions summaries, annotations, `logs/source_fetch_report.json`, and `data/source_health_state.json`.
- Do not add UI locales beyond `ja` and `zh-Hans` without explicit approval; English stays the default/canonical language.
- Do not remove or weaken the output escaping in `docs/app.js` (`escapeHtml` / `safeUrl`), and never render a source field as raw HTML. Treat ingested data as untrusted.
